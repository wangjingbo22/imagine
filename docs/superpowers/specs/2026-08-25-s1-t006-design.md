## 1. 目标与验收口径

本切片完成三个可独立验证、又能共同支撑后续规划的契约：

1. 同名 POI 的缓存读写以 `cityCode` 隔离。在线失败时只能返回相同
   `provider + operation + cityCode + requestHash` 的缓存，不得串城。
2. Provider 缺失或非法价格统一表示为
   `amountCents = None + sourceStatus = UNKNOWN`。`UNKNOWN` 不是免费，也不能
   变成 `0`。
3. 预算汇总只产出“已知金额小计”。每个未知价格产生可定位预警，使汇总状态
   进入 `NEEDS_CONFIRMATION`；未知项不参与已知金额求和。

仓库交接还要求 T006 把当前团队的归一化路线快照接到 T009
`RouteRiskInput`。仓库中没有名为 `RouteSnapshot` 的模型，实际可用的稳定来源契约
是 `app.domain.models.Route`。本设计把纯 `Route -> RouteRiskInput` 适配作为 T006
集成切片：它复用 `Route.routeId` 作为稳定 `routeSegment`，不访问 Provider，不改写
T009 规则，也不进入 T010/T011 的 UI 或规划器。该桥接是显式交接要求、体量可控，
并直接解除下游 DTO 接入阻塞，因此不属于越界。

## 3. 方案比较

### 方案 A：补强现有边界（推荐）

保留现有 SQLite 和 `AmapLocationService`；用更强验收测试冻结 cityCode 复合键。
在领域层新增纯预算汇总模块，并强化 `PriceFact` 双向不变量。在应用层新增无 I/O 的
路线风险适配器。

优点是改动小、遵循现有分层、可以分别测试，而且不会重复实现已正确工作的缓存。
代价是预算汇总是新的内部契约，调用方必须显式查看 `status/warnings`，不能把
`knownSubtotalCents` 当完整总额。

### 方案 B：由 `AmapLocationService` 直接返回预算摘要

地点/路线接口在 Provider 响应中附带预算小计和预警。

这会让 Provider 编排层承担跨项目的预算规则，并扩张尚未登记的 HTTP 响应；地点和
路线还会重复汇总逻辑。它不利于后续把用户确认价或其他来源纳入同一预算，因此不选。

### 方案 C：直接修改 PlanVersion/规划器的任务金额模型

把 `PlanTask.costCents` 改为可空，再在 T010/T011 中传播 unknown。

这能覆盖更长链路，但会修改 Plan 快照不变量、前端和规划器，超出 T006 2h 切片，
还可能破坏已冻结的 Plan V1/V2 契约，因此明确拒绝。

## 5. 缓存隔离契约

权威缓存键保持：

```text
(provider, operation, city_code, request_hash(canonical parameters))
```

`request_hash` 使用 UTF-8 JSON，键排序且无多余空白。地点查询参数本身也含
`cityCode`，形成“独立 city_code 列 + 摘要内 cityCode”的双重隔离。实现不新增
字符串拼接键，也不把高德 Key、payload 或用户敏感信息写入快照。

验收场景使用同一关键词“城市博物馆”、相同分页与类型，分别写入北京 `110000` 和
上海 `310000` 的不同 POI。随后两个在线调用都失败：北京必须恢复北京 POI，上海必须
恢复上海 POI，来源均为 `VERIFIED_CACHE`。测试从临时 SQLite 只读查询键列，与
`tests/snapshots/s1_t006_cache_keys.json` 比较：

```json
[
  {
    "provider": "AMAP",
    "operation": "place_search",
    "cityCode": "110000",
    "requestHash": "2e0661f0a04ac1e591a39979ea61f5ce3f0c0a5ec9ab7536492d0710b2eec9c5"
  },
  {
    "provider": "AMAP",
    "operation": "place_search",
    "cityCode": "310000",
    "requestHash": "49e5ec5dfe9a06e4ebaeaf58c872d64bc95f564a8b547f1e2bacb82e4e127e2d"
  }
]
```

若相同参数的目标城市没有缓存，继续抛出原在线 `AppError`；不尝试其他城市、过期
策略以外的模糊命中或无城市键。

## 6. 来源归一化与预算契约

### 6.1 `PriceFact` 双向不变量

`PriceFact` 必须满足且仅满足下列两种状态：

| `amountCents` | `sourceStatus` | 含义 |
|---|---|---|
| 非负整数（包括 0） | 非 `UNKNOWN` | 已知金额；0 可表示真实免费 |
| `None` | `UNKNOWN` | 金额未知，等待确认 |

因此 `None + ONLINE` 和 `0 + UNKNOWN` 都在模型边界拒绝。缓存恢复未知价格时，价格
事实继续是 `UNKNOWN`，同时保留缓存记录的 `fetchedAt/isStale`；集合本身仍标记
`VERIFIED_CACHE`，两层来源语义不可互相覆盖。

### 6.2 新增内部领域接口

`app/domain/budget.py` 定义：

```python
class BudgetStatus(StrEnum):
    COMPLETE = "COMPLETE"
    NEEDS_CONFIRMATION = "NEEDS_CONFIRMATION"

class BudgetLine(BaseModel):
    referenceId: NonBlankText
    priceFact: PriceFact

class BudgetWarning(BaseModel):
    code: Literal["UNKNOWN_PRICE"] = "UNKNOWN_PRICE"
    referenceId: NonBlankText
    kind: NonBlankText
    message: Literal["价格未知，未计入已知金额小计"] = "价格未知，未计入已知金额小计"

class BudgetSummary(BaseModel):
    knownSubtotalCents: int = Field(ge=0)
    unknownAmountCount: int = Field(ge=0)
    status: BudgetStatus
    warnings: list[BudgetWarning]

def summarize_budget(lines: Iterable[BudgetLine]) -> BudgetSummary: ...
```

汇总按输入顺序稳定地产生预警。已知金额（包括真实 0）进入
`knownSubtotalCents`；未知金额不进入算术表达式，每项生成一个 `UNKNOWN_PRICE`
预警。存在任何预警时状态为 `NEEDS_CONFIRMATION`，否则为 `COMPLETE`。

字段刻意命名为 `knownSubtotalCents`，不提供 `totalCostCents`，以阻止调用方把不完整
金额误认为完整预算。该汇总不判断是否超预算；T010/T011 若消费它，必须先处理
`NEEDS_CONFIRMATION`，再形成正式 Plan 金额。

## 7. `Route -> RouteRiskInput` 集成切片

### 7.1 范围结论

本适配属于 T006：交接文档明确把 Provider 归一化路线到 T009 DTO 的桥接指派给
T006，而且它是无 I/O、无规划决策的窄接口。以下工作仍越界：组合多日/多段候选、
插入休息任务、调用 T009 evaluator、编译约束、修改 T010/T011 页面或规划器。

### 7.2 接口和确定性映射

`app/application/route_risk_adapter.py` 提供：

```python
class RouteRiskAdapterError(ValueError):
    code: str
    route_segment: str
    field: str

def route_snapshot_to_risk_input(
    route_snapshot: Route,
    *,
    elapsed_since_rest_minutes: int,
) -> RouteRiskInput: ...
```

当前一个 `Route` 表示起终点间一个已选路线快照，映射为一个
`RouteSegmentRiskFacts`：

| T009 字段 | 来源/规则 |
|---|---|
| `routeSegment` | 原样使用 `Route.routeId`；不得重新编号或散列 |
| `walkingDistanceMeters` | `WALKING` 使用 `distanceMeters`；`TRANSIT` 必须使用非空 `walkingDistanceMeters`；`DRIVING/BICYCLING` 为 0 |
| `cumulativeTransfers` | `TRANSIT` 必须使用非空 `transferCount`；其他模式为 0 |
| `elapsedSinceRestMinutes` | 由调用方显式提供日程中的累计值；适配器校验它是整数且不小于 `ceil(durationSeconds / 60)` |
| `walkTypes` | `WALKING/TRANSIT` 为 `(UNKNOWN,)`，因为现有 Provider 快照没有结构化阶梯证据；零步行模式为 `(LEVEL,)` |

使用相同累计休息间隔重复映射同一个 `Route` 必须得到字节一致的
`model_dump_json(by_alias=True)`。`UNKNOWN` 不能替换为 `LEVEL` 来让避楼梯规则通过；
T009 会据此返回 `NEEDS_CONFIRMATION` 并带回同一 `routeSegment`。

`Route` 本身不含“上次休息”日程语义，因此 T006 不用路线时长冒充累计休息间隔。
T010/T011 组合候选时负责提供这个值；T006 只验证它至少覆盖本段路线时长，再写入
T009 DTO。这样既不把规划器纳入 T006，也不会因低估休息间隔产生假 PASS。

### 7.3 失败语义

适配器对 T009 必需但 Provider 快照缺失的事实 fail-closed：

- `TRANSIT.walkingDistanceMeters is None`；
- `TRANSIT.transferCount is None`；
- `elapsed_since_rest_minutes` 不是整数，或小于向上取整后的本段路线分钟数；
- `routeId` 超过 T009 的 120 字符上限。

以上均抛 `RouteRiskAdapterError`，其中
`code = "ROUTE_RISK_INPUT_INVALID"`，`route_segment` 为原 `routeId`，`field` 为具体
缺失/非法字段。错误不转换为零，不吞掉，也不在本切片注册新的 HTTP 错误码。
