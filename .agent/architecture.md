# 项目架构规范

> 项目尚未最终确定，本文件先固化“架构底线”和“通用分层规则”。项目名称、技术栈、具体模块边界在立项后补充，不允许由 AI 擅自替代人工决策。

## 1. 必须人工产出的内容

以下内容必须由人工先定，再进入 AI 辅助开发阶段：

- 需求文档：用户故事、验收标准、优先级
- 架构设计：模块划分、技术选型及理由、数据流向
- 接口定义：URL、参数、返回值、异常码、一致性校验
- 数据设计：实体关系、表结构、索引、状态流转
- 测试设计：测试场景、断言逻辑、边界条件

## 2. 项目基础信息

- 项目名称：行知旅伴——面向国内城市的预算约束与关怀出行 AI Agent
- 技术栈：React + FastAPI + LangGraph（2026-08-24 由张琪确认）
- 架构模式：前后端分离 + Agent Flow
- 部署形态：公网响应式 Web；本地开发与录屏作为回退

### 2.1 PBI-02-A 模块边界

- 表现层：仅调用地点、地理编码与路线 HTTP API，不接触高德 Key 或 SQLite。
- 应用层：编排在线查询、字段归一化和同城缓存降级。
- 领域层：维护 CityContext、Place、Route、PriceFact、Provenance 等稳定类型。
- 基础设施层：封装高德 Web 服务和 SQLite 缓存。
- 本模块不负责行程规划、预算决策、PlanVersion 状态机或 LangGraph 核心编排。

### 2.2 PBI-04-B Plan V1 模块边界

- 表现层：只提交方案候选、显式确认和开始执行命令；刷新时按 `tripId` 恢复状态，不直接操作 SQLite。
- 应用层：`PlanVersionService` 统一转换存储冲突和状态错误，不允许页面绕过用例入口。
- 领域层：`plan_guard.py` 维护 Trip 与 PlanVersion 的合法迁移；`plan.py` 维护不可变快照及金额、步行、任务顺序和硬约束不变量。
- 基础设施层：SQLite 在同一事务内更新 Trip/PlanVersion，并用部分唯一索引保证每个 Trip 最多一个 `CURRENT`。
- 当前持久化文件默认是 `data/plan_versions.sqlite3`，可用 `PLAN_VERSION_DB_PATH` 覆盖。
- LangGraph/LLM 只能提出 `PROPOSED` 数据，不具备确认或直接改写状态的权限。

## 3. 通用分层规范

### 3.1 表现层

- 负责页面展示、用户交互、输入输出适配
- 不直接承载复杂业务规则
- 不直接读写数据库或底层存储

### 3.2 应用层

- 负责流程编排、用例协调、事务边界控制
- 对接表现层和业务层
- 不直接耦合具体 UI 细节

### 3.3 业务层

- 负责核心业务规则、状态流转、校验逻辑
- 保持领域语义稳定
- 禁止混入大量框架样板逻辑

### 3.4 基础设施层

- 负责数据库、缓存、消息、文件、第三方服务、设备能力等外部依赖
- 提供清晰接口给上层调用
- 屏蔽实现细节和环境差异

## 4. 模块边界原则

- 模块之间通过契约协作，不直接依赖内部实现
- 公共模块只能沉淀稳定通用能力，禁止变成“杂物间”
- 认证、订单、支付、流程编排等核心链路需要单独标识负责人
- 禁止跨层调用破坏职责边界

## 5. 数据流向原则

默认遵循如下链路：

`用户输入/外部事件 -> 表现层 -> 应用层 -> 业务层 -> 基础设施层 -> 数据源或外部系统`

返回链路：

`数据源或外部系统 -> 基础设施层 -> 业务层 -> 应用层 -> 表现层 -> 用户可见结果`

如存在 AI 流程或状态图，则补充：

`触发事件 -> 流程编排节点 -> 工具/服务调用 -> 状态更新 -> 结果输出`

## 6. 架构硬约束

- Controller / Page / UI 组件不得直接操作数据库
- 业务规则不得散落在多个页面事件中
- DTO / VO / Entity / State 等数据对象职责要清晰
- 日志、异常、鉴权、校验等横切能力优先统一封装
- 涉及核心安全逻辑和核心业务规则的模块应列入禁飞区
