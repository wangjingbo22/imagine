## 3. 通用分层规范

### 3.1 表现层

- 负责页面展示、用户交互、输入输出适配
- 不直接承载复杂业务规则
- 不直接读写数据库或底层存储

### 3.2 应用层

- 负责流程编排、用例协调、事务边界控制
- 对接表现层和业务层
- 不直接耦合具体 UI 细节

### 3.3 业务层

- 负责核心业务规则、状态流转、校验逻辑
- 保持领域语义稳定
- 禁止混入大量框架样板逻辑

### 3.4 基础设施层

- 负责数据库、缓存、消息、文件、第三方服务、设备能力等外部依赖
- 提供清晰接口给上层调用
- 屏蔽实现细节和环境差异

## 4. 模块边界原则

- 模块之间通过契约协作，不直接依赖内部实现
- 公共模块只能沉淀稳定通用能力，禁止变成“杂物间”
- 认证、订单、支付、流程编排等核心链路需要单独标识负责人
- 禁止跨层调用破坏职责边界

## 5. 数据流向原则

默认遵循如下链路：

`用户输入/外部事件 -> 表现层 -> 应用层 -> 业务层 -> 基础设施层 -> 数据源或外部系统`

返回链路：

`数据源或外部系统 -> 基础设施层 -> 业务层 -> 应用层 -> 表现层 -> 用户可见结果`

如存在 AI 流程或状态图，则补充：

`触发事件 -> 流程编排节点 -> 工具/服务调用 -> 状态更新 -> 结果输出`

## 6. 架构硬约束

- Controller / Page / UI 组件不得直接操作数据库
- 业务规则不得散落在多个页面事件中
- DTO / VO / Entity / State 等数据对象职责要清晰
- 日志、异常、鉴权、校验等横切能力优先统一封装
- 涉及核心安全逻辑和核心业务规则的模块应列入禁飞区
